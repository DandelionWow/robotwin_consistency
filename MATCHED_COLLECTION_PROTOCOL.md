# Matched Expert–Pi0.5 collection protocol

Status date: 2026-10-07

## Scope and current gate

The smoke dataset is fixed to:

```text
3 tasks × 2 env seeds × {expert, pi05}
= 6 matched pairs
= 12 trajectories
```

Collection is currently blocked until a Pi0.5 checkpoint/config is proven
runnable by the checked-in RoboTwin Pi0.5 loader. The collector must fail
before simulation if checkpoint identity, assets/norm stats, config, or code
provenance is incomplete.

Old `/data1/liuwenhao/Datasets/data` episodes are not a fallback: their
episode-to-seed mapping, episode-level failure label, policy checkpoint, and
exact task config are not confirmed.

## Pair execution rule

One invocation of `experiments/policy_shift/collect_matched_pair.py` accepts one
task, one integer `env_seed`, and one Pi0.5 config. It performs both sides in
the same Python process:

```text
resolve immutable code/config/checkpoint provenance
  -> construct expert scene with task + env_seed
  -> capture canonical initial state and first head RGB
  -> execute and record expert trajectory
  -> close/reset environment
  -> construct Pi0.5 scene with identical task + env_seed + config
  -> capture canonical initial state and first head RGB
  -> hard-check state_fingerprint
  -> execute and record Pi0.5 trajectory
  -> validate cadence/schema/files
  -> atomically publish one pair manifest
```

The sides must not be generated by unrelated jobs and joined later by seed.

The identifier is exactly:

```text
pair_id = {task}__seed{env_seed}
```

Every formal invocation also receives the committed machine-readable seed plan
`experiments/policy_shift/configs/matched_smoke_seed_plan.json`. The collector
hard-fails if its task/seed is absent and stores the plan SHA256 in the pair
manifest.

## Pre-action state gate

Before any expert or policy action, capture:

- actual left/right robot joint state and gripper state;
- realized left/right EEF xyz and quaternion;
- camera intrinsic, extrinsic, and camera-to-world matrices;
- every scene actor name, xyz, and quaternion, sorted by actor name;
- task/domain-randomization parameters;
- table/background/light parameters exposed by the task;
- the first head RGB frame.

For the state fingerprint:

1. recursively sort mapping keys;
2. sort actor records by actor name;
3. reject NaN/infinity;
4. quantize floats to `1e-6`;
5. serialize canonical compact JSON;
6. compute SHA256.

The head first-frame SHA256 is saved as a render diagnostic. Pixel identity is
not the only hard criterion because renderer/denoiser implementations may be
nondeterministic.

Pair status is one of:

```text
STATE_MATCH
STATE_MISMATCH
UNKNOWN
```

Only `STATE_MATCH` is formally eligible. A mismatch terminates the pair before
the policy rollout is admitted to the dataset.

## Common sampling cadence

Expert and Pi0.5 must be sampled by the same physics-step recorder, not by two
different video recorders. Record:

```text
physics_timestep
physics_steps_per_sample
raw_fps
raw_frame_dt
bwm_sampling_stride
effective_bwm_fps
effective_frame_dt
```

With the default RoboTwin timestep `1/250 s`, sampling every 25 physics steps
produces a 10 Hz raw trajectory. The exact values used by a run must be stored
in the pair manifest. Expert and policy effective FPS must compare equal or the
pair hard-fails.

MP4 metadata is only an encoding field; it does not establish model cadence by
itself.

## Required trajectory content

Each side preserves the raw observations necessary to establish BWM input
semantics:

- head RGB frames;
- realized left/right EEF xyz + quaternion (`wxyz`);
- realized/recorded gripper state;
- actual robot state;
- frame timestamps derived from physics steps;
- camera intrinsics/extrinsics;
- instruction;
- explicit task success boolean and its source;
- trajectory length and cadence;
- for Pi0.5, every raw policy command before the simulator/controller;
- for expert, the executed expert path identity.

Raw policy commands are archived for provenance only. They are never passed to
BWM `eef_abs`; BWM conditioning always comes from the recorded realized EEF
trajectory.

## Pi0.5 preflight

Before environment creation, verify:

- the checkpoint directory is the exact path used by RoboTwin `pi_model.py`;
- the complete inference checkpoint exists and receives one canonical manifest
  identity: for Orbax/JAX this covers every file under `params/` and `assets/`
  plus `_CHECKPOINT_METADATA` when present; for PyTorch this covers
  `model.safetensors` and `assets/`;
- each manifest entry records relative path, byte size, and SHA256; hashing one
  arbitrary OCDBT shard is not a valid checkpoint identity;
- the `assets/<asset_id>` norm-stat assets exist;
- `train_config_name`, `model_name`, `checkpoint_id`, and `pi0_step` are fixed;
- the referenced OpenPI training config exists in the checked-in model code;
- observation preprocessing and action convention are recorded;
- a model-load smoke test completes on GPU 0–3, or on the explicitly
  authorized remote-server exception GPU 5; the physical index is recorded.
- `nvidia-curobo` is an editable install from the explicitly supplied clean
  CuRobo checkout; its git commit, distribution version, Torch build, CUDA
  build, device name, compute capability, and compiled architecture list are
  recorded in every pair manifest.

Possible local weight files whose compatibility is not yet established must not
be auto-selected. A task-specific checkpoint also must not be silently reused
as a general three-task policy.

## Output and overwrite rules

Proposed layout:

```text
outputs/policy_shift/matched_raw/
  <pair_id>/
    manifest.json
    expert/
      data/episode0.hdf5
      video/episode0.mp4
      initial_state.json
    pi05/
      data/episode0.hdf5
      video/episode0.mp4
      initial_state.json
      raw_policy_commands.npy
```

An existing pair directory is never overwritten implicitly. Collection writes
to a staging directory and publishes the pair only after both sides and all
hard checks pass.

## Dataset-level acceptance

Smoke A passes only when all six requested pairs satisfy:

- complete hashed provenance;
- explicit Expert/Pi0.5 success labels;
- `STATE_MATCH`;
- common realized-EEF schema;
- equal effective cadence;
- both trajectory lengths at least 81;
- no missing HDF5/video/instruction/camera record;
- no duplicate `pair_id`.

The dataset-level audit reports excluded pair count, task distribution, expert
short count, and policy short count. It never silently drops a side or pads a
short trajectory.
